# 03. 主 Notebook 规范

## 1. Notebook 定位

`notebooks/main_analysis.ipynb` 是项目的总控执行文件，也是分析叙事文档和交互式分析工作台。

它必须承担以下职责：

- 读取并确认 `docs/analysis_framework.md`。
- 读取并确认 `reports/final/final_report_structure.md`。
- 读取并确认 `docs/change_execution_log.md` 中当前变更的影响范围和重跑起点。
- 说明本次分析基于的业务背景、决策目标、核心业务问题和分析边界。
- 加载环境、配置和依赖。
- 连接数据库。
- 调用 Python 脚本执行 SQL 文件。
- 加载和校验数据。
- 调用 Python 模块完成清洗、特征、分析、建模和可视化。
- 展示关键中间结果。
- 导出图表、表格和报告输入素材。
- 支撑脚本生成结果呈现型最终报告。

Notebook 不应承担大量底层函数定义。复杂逻辑必须下沉到 `src/` 目录中的 Python 脚本。

数据分析通常不是一次从头到尾完成的线性工作。Notebook 必须支持分析师围绕某个中间步骤局部调试、调整逻辑并继续运行；变更验证时必须运行到最远受影响正式产物，正式发布按 `docs/09_change_management_standard.md` 执行完整运行。

## 2. Notebook 章节生成规则

主 Notebook 基于 `templates/notebook_sections.yaml` 生成，章节开关由 `project.yaml` 控制。所有项目必须包含以下核心章节：

```text
1. 分析框架确认
2. 环境、依赖与配置加载
3. 数据源与字段理解
4. 数据加载
5. 数据质量检查
6. 数据清洗与转换
7. 探索性数据分析
8. 核心业务问题分析
9. 结果验证与稳健性检查
10. 图表、表格和报告输入素材导出
11. 项目完成检查
```

以下章节只在对应配置启用时生成：

| 章节 | 配置条件 |
| --- | --- |
| 数据库连接与 SQL 执行 | `modules.database: true` |
| 统计分析 | `modules.statistics: true` |
| 机器学习建模 | `modules.modeling: true` |
| 最终报告生成 | `deliverables.final_report: true` |

不适用章节不进入生成结果，原因由 `project.yaml` 记录。修改配置后可运行 `python scripts/generate_notebook.py` 重新生成骨架，但正式分析阶段必须先确认覆盖影响。

## 3. Notebook 备注规范

每一个主要步骤之前必须有 Markdown 说明。禁止只写代码而不解释目的。

每个大章节只保留一个标题，例如：

```markdown
## 步骤 XX：步骤名称
```

标题下面的备注内容统一使用正文，不再使用 `### 目的`、`### 输入`、`### 输出` 这类多层小标题。如果确实需要强调某一项，使用加粗正文标签即可，例如：

```markdown
## 步骤 XX：步骤名称

**目的：** 说明本步骤要解决什么问题。

**上游依赖：** 说明运行本节前必须完成哪些章节、确认哪些口径或准备哪些对象。

**输入文件/对象：** 说明使用哪些数据表、SQL 文件、配置文件、数据文件、DataFrame 或中间对象。

**输出文件/对象：** 说明本步骤会生成哪些 DataFrame、图表、结果表、中间文件或报告素材。

**是否可缓存：** 说明本节中间结果是否可以落地复用，以及哪些变更会导致缓存失效。

**调试提示：** 说明人工调试本节时常见的回退章节、风险、限制或需要复核的内容。
```

关键代码 cell 上方必须有简短说明，尤其是以下内容：

- 数据库连接。
- SQL 脚本执行。
- 数据清洗规则。
- 指标计算逻辑。
- 统计检验方法。
- 特征工程规则。
- 模型训练和评估逻辑。
- 图表导出逻辑。
- 最终结果保存逻辑。

如果某一节的逻辑会频繁迭代，应该在备注中说明它的缓存位置、重跑条件和下游影响范围，方便分析师局部调试，而不是每次完整执行整个 Notebook。

## 4. Notebook 执行规范

Notebook 必须满足：

- 可以从第一个 cell 到最后一个 cell 顺序执行。
- 日常分析允许局部运行；变更验证必须到最远受影响产物，正式发布按变更规范完整顺序运行。
- 局部运行时应依赖明确的输入文件、缓存文件或上游对象，不应依赖无法追溯的隐藏变量。
- 不依赖历史执行状态或手动修改内存对象生成最终交付结果。
- 不保留无关实验代码、失败代码和临时调试输出。
- 不在 Notebook 中硬编码数据库密码、密钥、个人路径或敏感参数。
- 所有随机过程必须设置随机种子。
- 所有关键输出必须保存为文件。

建议在 Notebook 开头设置以下项目参数：

- 项目名称。
- 分析日期。
- 数据时间范围。
- 运行环境。
- 随机种子。
- 输出目录。
- 是否连接生产数据库。
- 是否只读执行 SQL。
- 当前变更编号。

## 5. Notebook 代码组织原则

Notebook 应负责组织流程和呈现结果，不应堆积大量函数定义。

适合留在 Notebook 中的内容：

- 项目背景和分析目标。
- 参数设置和配置读取。
- 调用 `src/` 函数的流程代码。
- 展示关键中间结果。
- 对图表、统计结果、模型结果的解释。
- 导出报告输入素材。

应该下沉到 `src/` 的内容：

- 数据库连接。
- SQL 文件读取和执行。
- 数据质量检查函数。
- 清洗和转换函数。
- 指标计算函数。
- 特征工程函数。
- 统计检验函数。
- 模型训练和评估函数。
- 通用绘图函数。
- 结果导出函数。

## 6. 主 Notebook 骨架维护

主 Notebook 的标准骨架以 `templates/notebook_sections.yaml` 为唯一来源，`notebooks/main_analysis.ipynb` 是根据 `project.yaml` 生成的实际执行入口：

```text
notebooks/main_analysis.ipynb
```

本文档不再完整复制 Notebook 内容，避免规范文档和实际模板两边漂移。维护规则如下：

- 修改 Notebook 章节顺序时，同步更新本文档第 2 节的章节清单。
- 修改章节备注字段时，同步更新本文档第 3 节的备注规范。
- 修改主 Notebook 的执行、缓存或交付前检查规则时，同步更新本文档对应规范。
- 修改变更工作流或完成检查规则时，同步更新 `docs/09_change_management_standard.md`。
- 项目交付时，以 `notebooks/main_analysis.ipynb` 的实际内容和 `docs/08_reproducibility_audit_checklists.md` 的审计清单为准。

主 Notebook 必须继续覆盖以下核心阶段：

```text
分析框架确认
→ 环境、依赖与配置加载
→ 数据库连接与 SQL 执行说明
→ 数据源与字段理解
→ 数据加载
→ 数据质量检查
→ 数据清洗与转换
→ 探索性数据分析
→ 业务问题分析
→ 可选统计分析或机器学习建模
→ 结果验证与稳健性检查
→ 图表、表格和报告输入素材导出
→ 最终报告脚本生成
→ 项目完成检查
```

## 7. 交付前 Notebook 清理要求

交付前必须清理：

- 无关实验代码。
- 失败代码。
- 临时打印。
- 只服务调试的中间输出。
- 未使用变量和未使用导入。
- 与项目无关的图表。

交付前必须确认：

- 所有 cell 已按顺序运行。
- 没有报错。
- 输出文件已生成。
- 图表和结果表路径正确。
- reports/final/report_inputs.yaml 已生成。
- docs/script_catalog.md 已覆盖可直接执行脚本，且脚本变更已同步更新该文档。
- 最终报告由 scripts/generate_final_report.py 生成。
- 当前变更日志中的受影响环节、检查项和剩余风险已更新。
