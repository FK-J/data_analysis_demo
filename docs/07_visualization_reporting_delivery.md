# 07. 可视化、报告与交付规范

报告计划以项目契约 `report_requirements` 为验收目录，素材 `coverage` 声明每项覆盖与依据。报告核心数值使用注册指标 ID 和结果表单元格引用；正式生成前自动对账，生成后保存报告指纹及运行 ID。样张和最终结论的业务合理性仍需人工审阅。

## 1. 可视化总体原则

图表必须服务于结论。

必须遵守：

- 图表类型与数据关系匹配。
- 标题简洁明确。
- 坐标轴、单位、时间范围清晰。
- 分类过多时进行合理排序或合并。
- 颜色使用有含义，避免过度装饰。
- 不使用误导性坐标轴。
- 不隐藏关键异常值，除非明确说明。

禁止输出没有解释、没有业务含义、没有后续使用价值的图表。

## 2. 图表信息要求

每张关键图表必须包含：

- 图表标题。
- 横轴和纵轴含义。
- 单位。
- 时间范围。
- 数据口径。
- 必要的图注。

如果图表经过抽样、过滤、截尾、标准化或聚合，必须在 Notebook 中说明。

## 3. 图表导出要求

关键图表必须导出到：

```text
reports/figures/
```

建议图表命名格式：

```text
fig_01_metric_trend.png
fig_02_segment_comparison.png
fig_03_model_performance.png
```

Notebook 中展示的关键图表，必须能在 `reports/figures/` 中找到对应文件。

## 4. 结果表导出要求

关键结果表必须导出到：

```text
reports/tables/
```

常见结果表包括：

- 数据质量检查汇总。
- 核心指标汇总。
- 分组对比结果。
- 统计检验结果。
- 模型评估结果。
- 关键样本清单，若权限允许。

结果表必须字段清晰、命名明确，并避免包含未脱敏敏感信息。

## 5. 报告结构与交付规范

最终交付必须包含脚本生成的两份结果呈现型报告，而不是只交付图表、结果表或 Notebook 输出：

| 产物 | 路径 | 内容 |
| --- | --- | --- |
| 结论摘要 | `reports/final/final_analysis_report.md` | 元数据与运行 ID、核心结论、关键指标、关键图表、交付物索引 |
| 分析详情 | `reports/final/analysis_detail.html` | 分析框架、数据范围与质量、清洗、EDA、逐问题分析过程与证据、全量图表和结果表、口径限制、每节结论、复现信息 |

正式分析前必须先确认两份产物的结构：

```text
reports/final/final_report_structure.md
```

报告结构模板为：

```text
docs/final_report_structure_template.md
```

### 5.1 结论摘要

结论摘要只允许包含：

- 元数据与运行 ID。
- 核心结论。
- 关键指标。
- 关键图表。
- 交付物索引，链接到分析详情对应章节。

结论摘要不得展开逐业务问题的分析逻辑、分析过程、图表清单、结果表清单、数据质量明细、清洗步骤和复现细节。详细内容统一放在分析详情。

结论摘要成品结构见：

```text
docs/final_analysis_report_template.md
```

### 5.2 分析详情

分析详情必须包含：

- 分析概览：核心结论、关键指标、关键图表。
- 每个业务问题：本节目标、**本节结论**、分析逻辑、分析过程、核心指标、图表、结果表、口径与限制。
- 跨问题过程章节：数据质量、清洗、EDA、稳健性、方法假设等，每个章节同样必须有**本节结论**。
- 附录与复现信息：数据范围、指标口径、输出文件、报告要求覆盖、运行 ID 和复现路径。

分析详情成品结构、锚点和安全要求见：

```text
docs/analysis_detail_report_template.md
```

### 5.3 生成、绑定与链接

两份产物必须由 `scripts/generate_final_report.py` 基于 `reports/final/report_inputs.yaml` 在同一次执行中生成，并绑定同一个运行 ID。

结论摘要中的交付物索引必须链接到分析详情的稳定锚点；分析详情页头必须提供返回结论摘要的链接。

后续修改影响报告时，必须重新生成受影响图表、表格、报告输入和两份报告产物。准备正式交付时，先从头到尾顺序执行主 Notebook，再运行报告生成脚本。

脚本命令、参数、输入输出和写文件行为统一维护在：

```text
docs/script_catalog.md
```

### 5.4 交付要求

最终交付文件保存到：

```text
reports/final/
```

交付内容必须能够回答：

- 本次分析服务什么业务决策？
- 业务问题是如何拆解的？
- 汇总结果是什么？
- 每个业务问题对应的结果和结论是什么？
- 对应图表和结果表在哪里？
- 口径、限制和输出文件是什么？

禁止只交付代码或 Notebook，而不提供面向业务理解的结论。

禁止绕过 `scripts/generate_final_report.py` 手工拼接报告，除非用户明确要求。

禁止默认生成大模型洞察或业务解读。只有用户明确要求时，才可以渲染或加入洞察内容；洞察内容放在分析详情中。

禁止在结论摘要中重复分析详情的完整过程；两份产物内容重复时应删除摘要中的过程段落并改为链接。

## 6. 结果与可选洞察表达规范

默认两份产物只呈现结果，不自动生成洞察、归因、业务建议或扩写解读。用户明确要求加入洞察时，洞察内容写入分析详情，并在结论摘要中只保留结论和索引。

如果用户明确要求加入洞察或业务解读，则洞察内容必须区分：

- 事实。
- 推断。
- 建议。
- 局限性。

可选洞察建议采用以下表达结构：

```markdown
## 核心发现

1. 发现一：说明具体数据事实、影响范围和业务含义。
2. 发现二：说明分组差异、趋势变化或异常现象。
3. 发现三：说明需要关注的风险或机会。

## 业务建议

1. 建议一：说明建议动作、目标对象和预期影响。
2. 建议二：说明执行优先级和验证方式。

## 风险与局限性

1. 数据局限：说明数据覆盖、质量或口径问题。
2. 方法局限：说明统计或模型方法的假设限制。
3. 业务局限：说明结论落地时需要额外验证的条件。

## 下一步

1. 需要补充的数据。
2. 需要验证的假设。
3. 可以开展的实验或监控。
```

## 7. 业务建议要求

默认两份产物不自动生成业务建议。

如果用户明确要求加入业务建议，则业务建议必须可执行。

建议应该说明：

- 建议动作。
- 目标对象。
- 预期影响。
- 执行优先级。
- 验证方式。
- 风险或前置条件。

禁止输出空泛建议，例如“继续优化”“加强运营”“提升转化”，除非说明具体动作和验证方法。

## 8. 局限性说明要求

分析详情必须说明局限性；结论摘要通过交付物索引指向对应的口径与限制章节。

常见局限性包括：

- 数据覆盖不足。
- 数据质量问题。
- 样本量不足。
- 指标口径限制。
- 时间窗口限制。
- 方法假设限制。
- 无法支持因果解释。
- 结果只适用于特定人群或场景。

局限性不是附带免责声明，而是帮助读者正确使用结论的必要信息。
