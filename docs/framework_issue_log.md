# 框架使用问题与迭代记录

本文档只记录框架、模板、工具或流程本身的缺陷、根因和改进建议。普通业务需求、数据质量问题和变更执行状态不在此重复维护。

- 业务契约变化记录在 `docs/analysis_framework.md`，并关联 `change_id`。
- 变更执行状态记录在 `docs/change_execution_log.md`。
- 数据质量问题记录在主 Notebook 或对应质量结果中。
- 框架问题的处理变更通过 `change_id` 与本文件关联。

## 1. 记录原则

- 发现框架问题时先创建最小问题记录，不得先绕行后完全依赖事后回忆。
- 当前工作受阻时，可以先记录现象、影响和临时处理；根因与长期方案可在变更关闭前补充。
- 每个问题必须判断是框架通用问题还是待判断问题。
- 问题日志不复制变更状态、检查结果或文件清单。
- 修复框架问题时必须创建变更执行记录，并在 `change_id` 字段关联。

## 2. 需要记录的情况

- 同类需求需要反复指导才能按正确流程完成。
- 规范之间冲突、职责重叠或存在无法执行的要求。
- Notebook、脚本或模板难以按文档复现。
- 缓存、新旧产物或隐藏状态导致结果不一致。
- 需要临时绕过现有流程才能继续。
- 自动校验出现系统性误报、漏报或无法覆盖的风险。
- 交付前发现的问题本可由框架提前阻止。

单次业务口径变化、报告内容调整或项目数据异常不自动构成框架问题。只有它们暴露出可复用的框架缺陷时才在此登记。

## 4. 类型判断

**框架通用问题：** 很可能在其他项目重复出现，或说明模板、职责、工作流、脚本、缓存或门禁存在缺口。

**待判断问题：** 当前证据不足。必须保留触发场景和临时处理，后续出现同类情况时重新判断。

项目特定业务需求不作为本日志类型；它由变更执行日志和业务框架承载。

## 5. 处理要求

形成改进建议时至少说明：

- 需要修改的规范、模板、Notebook、脚本或目录。
- 重复问题的根因和影响范围。
- 建议如何验证修复有效。
- 是否改变现有项目的执行方式。
- 关联的 `change_id`；尚未立项时写“暂无”。

问题状态只表示根因是否得到处理，不表示关联变更是否通过门禁。关联变更的状态只能查看 `docs/change_execution_log.md` 中的对应记录。

## 6. 检查时机

在以下节点检查是否出现新的框架问题：

- 业务框架或报告结构确认后。
- Notebook 局部调试或完整运行后。
- 需求变更验证后。
- 修改 SQL、`src/` 或 `scripts/` 后。
- 报告生成或发布门禁后。

交付审计只确认已出现的框架问题是否记录和关联，不在最后一次性补写历史。
