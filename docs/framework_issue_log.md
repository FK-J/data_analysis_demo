# 框架使用问题与迭代记录

本文档用于记录用户在使用本数据分析框架过程中遇到的问题、临时处理方式和框架改进建议。

它不是交付审计后的附加总结，而是贯穿项目全过程的使用记录。只要出现不满足用户需求、需要用户指导修改、流程不清楚、文档不足、脚本难用、Notebook 调试不顺或其他影响交付效率的问题，都应该及时记录，并判断是否属于框架通用问题。

## 1. 记录原则

- 问题发生时及时记录，不等到项目结束。
- 先保证当前分析交付可继续推进，再补充记录和改进建议。
- 每条记录都要区分“项目特定问题”和“框架通用问题”。
- 如果暂时无法判断是否通用，先标记为“待判断”，后续在类似项目中复核。
- 框架通用问题不等于立即修改框架；应先写清楚建议、影响范围和需要用户确认的改动。

## 2. 需要记录的情况

- 用户指出当前输出、口径、图表、报告结构或执行方式不符合需求。
- 用户需要反复指导 Agent 修改同类内容。
- 工作流、文档或 Notebook 备注无法支撑当前调试和交付。
- 脚本功能、参数、输入输出或安全边界不清楚。
- 需要临时绕过现有流程才能完成分析。
- 某个步骤造成新旧结果混用、缓存误用、重复执行或难以复现。
- 交付前发现问题本可以通过框架规则提前避免。

纯业务口径变更应优先记录到 `docs/analysis_framework.md` 的需求变更记录；如果该变更暴露出框架流程、模板或文档不足，也应同步记录到本文档。

## 4. 类型判断标准

**项目特定问题：** 只由本项目的数据、业务口径、用户偏好或一次性约束造成，不需要修改通用模板或工作流。

**框架通用问题：** 很可能在其他数据分析项目中重复出现，或说明现有模板、Notebook、脚本、文档职责、工作流节点存在缺口。

**待判断问题：** 当前信息不足，暂时无法确认是否通用。应记录触发场景和临时处理方式，后续在复盘或类似项目中再判断。

## 5. 框架迭代建议

当问题被判断为框架通用问题时，应至少说明：

- 需要修改的文档、模板、Notebook、脚本或目录规范。
- 建议修改的具体方向。
- 该修改解决什么重复问题。
- 是否会影响现有项目的执行方式。
- 是否需要用户确认后再实施。

## 6. 使用时机

在以下节点都应快速检查是否需要新增或更新记录：

- 确认业务分析框架后。
- 确认最终报告结构后。
- Notebook 局部调试或重跑后。
- 用户提出需求变更或修正意见时。
- 修改 SQL、`src/` 或 `scripts/` 后。
- 生成最终报告后。
- 交付前审计前。

交付前只做完整性检查：确认使用过程中出现的问题是否已记录、分类和处理，不把问题记录延后到最后一次性补写。
