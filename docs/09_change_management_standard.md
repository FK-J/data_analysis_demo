# 09. 后续修改工作流规范

## 1. 目的

本文档用于保证后续修改不会只停留在当前文件、当前 cell、当前图表或最终报告，而是按影响范围完成文档同步、重跑、校验和结果更新。

核心要求只有一条：

> 每次修改都必须先判断影响，从最早受影响环节执行到最远受影响产物，再确认所有相关内容已经同步。

## 2. 哪些修改需要执行本流程

以下情况必须先记录到 `docs/change_execution_log.md`：

- 新增或修改分析需求。
- 修改数据源、时间范围、分析对象或关联方式。
- 修改指标、筛选、清洗、总计、排名、统计或模型逻辑。
- 修改正式报告的结构、图表、表格或展示范围。
- 修改会影响分析结果或交付方式的 SQL、Python、Notebook 或脚本。

仅修正不影响含义和结果的错别字、代码注释或内部说明时，可以不单独记录，但仍应检查修改位置是否正确。

## 3. 变更等级

同一需求涉及多个等级时，按最高等级执行。

| 等级 | 判断标准 | 最小执行范围 |
| --- | --- | --- |
| L0 文案与样式 | 不改变数字、口径、样本和报告结构 | 修改目标内容，并检查相关页面或文件 |
| L1 报告与展示 | 源数字不变，只改变章节、表格、图表或展示对象 | 更新报告结构（如适用），重新导出受影响图表/表格并生成报告 |
| L2 计算与口径 | 输入总体不变，但修改指标、筛选、清洗、汇总、统计或模型逻辑 | 从最早受影响的计算环节运行到最终报告，并完成口径和质量校验 |
| L3 数据与业务框架 | 修改数据源、时间范围、粒度、关联、分析范围、核心问题或方法路线 | 先更新业务框架和报告结构，从数据加载或框架确认开始执行完整下游流程 |

边界判断：

- 只隐藏展示对象属于 L1；如果筛选影响分母、总计或排名，则属于 L2。
- 修改数据输入的人群、时间或实体范围属于 L3。
- 无法判断时先按较高等级执行，不直接开始修改。

## 4. 标准执行步骤

每次受管修改必须按以下顺序执行：

1. **登记需求：** 在 `docs/change_execution_log.md` 写明需求、等级和验收标准。
2. **判断影响：** 列出受影响的业务框架、报告结构、数据、SQL、Python、Notebook、图表、表格和报告。
3. **同步上游文档：** 业务契约变化时先更新 `docs/analysis_framework.md`；报告结构变化时先更新 `reports/final/final_report_structure.md`。
4. **实施修改：** 修改受影响的 SQL、Python、Notebook、配置或报告素材。
5. **执行受影响流程：** 从最早受影响环节运行到最远受影响产物，不能在当前 cell、表格或图表正确后停止。
6. **完成校验：** 检查数据质量、指标口径、总计、筛选范围、新旧结果差异和输出一致性。
7. **更新正式产物：** 重新生成受影响的图表、结果表、`report_inputs.yaml` 和最终报告。
8. **关闭记录：** 在变更日志中逐项确认完成情况，记录未完成项和风险。

标准流程：

```text
登记需求
-> 判断等级与影响
-> 同步业务框架/报告结构
-> 修改实现
-> 从最早受影响环节运行到最远产物
-> 校验结果
-> 更新最终报告
-> 完成记录
```

## 5. 重跑起点

| 修改内容 | 最早重跑位置 | 必须运行到 |
| --- | --- | --- |
| 业务问题、分析边界或方法路线 | 分析框架确认 | 最终报告 |
| 数据源、时间范围、粒度、关联键 | 数据加载与质量检查 | 最终报告 |
| SQL | SQL 执行 | 最终报告 |
| 清洗或特征规则 | 数据清洗与转换 | 最终报告 |
| 指标、筛选、占比、排名、总计 | 指标计算/业务问题分析 | 最终报告 |
| 图表或表格展示 | 可视化与结果导出 | 最终报告 |
| 非口径报告文案 | 报告输入或报告生成 | 最终报告 |

如果一个需求同时影响多个环节，必须选择最早的受影响环节作为起点。

## 6. 完成条件

出现以下任一情况时，不得把修改标记为完成：

- 没有写清需求、等级或验收标准。
- 业务框架或报告结构发生变化但未同步。
- 只修改了局部文件，没有运行受影响的下游流程。
- 仍在使用已经失效的旧缓存、旧表格或旧图表。
- 数据质量、口径、筛选、总计或结果差异没有检查。
- 图表、结果表、报告输入和最终报告没有同步更新。
- 存在失败或未完成项，但没有说明影响和下一步。

## 7. 完整运行要求

日常修改允许从最早受影响环节开始局部重跑，但以下情况必须从头到尾顺序执行 `notebooks/main_analysis.ipynb`，再生成最终报告：

- L3 修改完成后。
- 无法确认缓存或上游结果是否仍然有效。
- 准备交付或替换正式报告。

L2 修改在日常验证时可以从受影响环节开始；正式交付前仍必须完整顺序运行。

## 8. 文档职责

- `docs/change_execution_log.md`：记录每次修改的执行范围、完成情况和风险。
- `docs/analysis_framework.md`：维护当前有效的业务问题、口径、范围和方法。
- `reports/final/final_report_structure.md`：维护当前有效的报告结构。
- `docs/framework_issue_log.md`：只记录框架、模板、工具或流程本身的问题。
- `docs/08_reproducibility_audit_checklists.md`：负责最终交付审计。

执行状态只在 `docs/change_execution_log.md` 维护，其他文档不重复记录同一状态。

## 9. Agent 执行要求

用户提出后续修改时，Agent 必须：

- 先读取本规范和当前变更日志，再修改文件。
- 修改前说明变更等级、影响范围和计划重跑起点。
- 修改后继续执行受影响的下游环节，不以文件写入成功作为完成标准。
- 最终说明已更新的产物、已完成的校验和仍存在的风险。
